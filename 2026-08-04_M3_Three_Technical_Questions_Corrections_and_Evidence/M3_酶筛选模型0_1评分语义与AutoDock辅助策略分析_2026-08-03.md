# M3 酶筛选模型 0–1 评分语义与 AutoDock 辅助策略分析

日期：2026-08-03

## 1. 需要回答的问题

老师问的是：

```text
我们酶筛选模型最后是不是有一个 0–1 评分？
这个评分本身够不够？
需不需要额外加一个类似 AutoDock 的对接评分？
这个评分到底评价什么？
它是不是也在评价结合难易程度？
```

本报告只基于本地代码、配置、运行审计和会议纪要回源判断，不把记忆当证据。

## 2. 简短结论

当前 EnzymeCAGE 的 0–1 分数可以作为当前主任务的主排序分数：

```text
reaction → candidate enzyme ranking
```

但它不是 AutoDock 那种 docking score，也不是结合自由能。

最稳妥的结论是：

```text
EnzymeCAGE 的 0–1 分数是一个反应-酶兼容性 / 正例可能性 / 排序分数。它来自模型 raw logit 的 sigmoid，训练目标是反应-酶正负配对分类。模型输入中确实包含反应特征、酶序列特征、pocket-node ESM、GVP 结构特征、底物/反应中心与 pocket 几何注意力，因此可以间接学习与口袋和底物兼容性相关的统计信号。

但是，这个分数不是显式 docking energy，不搜索底物结合姿势，不输出 kcal/mol 级结合能，也不能直接解释为“结合难易程度”。AutoDock-style docking 更适合放在 Top-K 候选之后，作为可选的二级证据、软 rerank 或可解释性检查，而不是默认替代 EnzymeCAGE 主分数。
```

## 3. 证据链

### 3.1 0–1 分数怎么来的

代码来源（官方公开 EnzymeCAGE commit `255a05e167aabc70f6c0322a00702cdc9d6ebfbc`）：

```text
enzymecage/model.py
enzymecage/base.py
```

`EnzymeCAGE.forward()` 最后把所有特征拼接后过 MLP，输出一个标量：

```text
model.py:310-315
all_features = torch.cat(all_features, dim=-1)
output = self.mlp(all_features).squeeze(-1)
if self.sigmoid_readout:
    output = torch.sigmoid(output)
return output
```

`predict()` 阶段如果模型本身没有 sigmoid readout，就对 raw logit 做 sigmoid：

```text
model.py:317-328
pred = torch.cat(preds)
if not self.sigmoid_readout:
    pred = torch.sigmoid(pred)
return pred
```

`evaluate()` 也是同样逻辑：

```text
base.py:33-40
pred = torch.cat(preds)
target = torch.cat(targets)
if not self.sigmoid_readout:
    pred = torch.sigmoid(pred)
metric = self.calc_metric(pred, target, rxns)
```

所以：

```text
0–1 分数 = 模型 raw logit 经过 sigmoid 后的分数。
```

它可以叫 probability-like score，但不能直接叫物理概率或结合能。

### 3.2 训练目标是什么

代码来源（官方公开 EnzymeCAGE commit `255a05e167aabc70f6c0322a00702cdc9d6ebfbc`）：


```text

```

`calculate_loss()` 是逐行 BCE 后乘权重再平均：


数据集里标签来自 `Label` 列：



因此，当前模型学的是：

```text
这个 reaction-enzyme pair 像不像训练数据里的正例配对。
```

它不是用 docking energy、结合亲和力、Km、kcat、kcat/Km、过渡态稳定化能或实验活性值作为监督目标。

## 4. 这个 0–1 分数到底评价什么

推荐定义：

```text
EnzymeCAGE_score = learned reaction-enzyme compatibility score
```

中文可以说：

```text
反应-酶兼容性分数；
反应-酶正例可能性分数；
候选酶排序分数。
```

它评价的是：

```text
给定这个反应表示和这个酶表示，这个 pair 有多像训练集中已知的正例反应-酶配对。
```

它综合了：

1. 反应 DRFP；
2. 底物/分子构象；
3. reaction center；
4. 酶 sequence-level ESM；
5. pocket-node ESM；
6. GVP 结构特征；
7. pocket 与 substrate/reacting-center 的几何 attention。

但它不应该被定义成：

```text
结合自由能；
docking energy；
Km/kcat/kcat/Km；
实验活性值；
过渡态稳定化能；
绝对催化可行性概率。
```

## 5. 它是不是评价“结合难易程度”

答案是：

```text
只能说间接相关，不能说直接评价。
```

它能间接包含的部分：

```text
因为模型使用 pocket/结构特征、底物/反应中心信息和几何 attention，所以它可能学习到某些与底物进入 pocket、局部环境匹配、反应类型适配相关的统计规律。
```

它没有做的部分：

```text
没有把底物 dock 到活性位点；
没有搜索结合姿势；
没有计算物理结合能；
没有显式处理过渡态；
没有输出 "-7.2 kcal/mol" 这类 docking score；
没有直接预测 Km/kcat。
```

所以面对老师时应该说：

```text
EnzymeCAGE 分数不是直接的结合难易程度，但它包含 pocket/结构/底物相关特征，因此可能间接反映一部分结合与催化兼容性信号。
```

## 6. 要不要额外加 AutoDock

### 6.1 当前建议

不建议现在把 AutoDock-style docking 作为默认必须项，也不建议直接替代 EnzymeCAGE 分数。

建议采用：

```text
主排序：EnzymeCAGE_score
证据来源约束：EC/Rhea/相似反应 + D4 资产可用性
可选二级检查：对 Top-K 高价值候选做 AutoDock-style docking
```

### 6.2 为什么不建议一开始就强制加

第一，目标不同。

```text
EnzymeCAGE 当前训练目标是反应-酶正负配对分类，评估也是 AUC/Top-K/MRR/Hit 排序。
AutoDock 目标是给一个受体-配体 pose/energy 近似评价。
```

第二，酶促反应不等于简单结合。

```text
底物能结合，不代表姿势适合催化；
静态结构 docking 差，也不一定说明真实酶不能催化；
酶柔性、金属离子、辅因子、水、质子化状态和过渡态都会影响结果。
```

第三，docking 需要额外制定很多规则：

```text
用哪个结构；
活性位点 box 怎么定；
金属/辅因子/水怎么处理；
底物质子化/互变异构怎么处理；
docking 阈值怎么定；
docking score 怎么和 EnzymeCAGE score 融合。
```

这些不是纯工程细节，需要老师/生物化学侧裁定。

第四，我们刚做的 on-demand D4 测试已经说明结构/口袋层本身有缺失。

相关审计：

```text
custom/docs/enzyme_feature_expansion/ENZYMECAGE_LUCAPCYCLE_MODEL_TRAINING_RUN_2026-07-01/04_Local_Review_Audits/ENZYMECAGE_M3_SINGLE_ENZYME_ONDEMAND_D4_100UID_COVERAGE_RESOURCE_PROBE_RERUN1_RETURN_LOCAL_AUDIT_2026-08-03.md
```

结果显示 100 个缺失 pocket/D4 UID 里只有 16 个达到 strict full D4 loader PASS。主要 blocker 是 AlphaFill 无可用 transplant、AlphaFill 404、pocket extraction 失败等。Docking 对结构和活性位点准备要求更高，如果直接作为默认全量步骤，会引入更重的失败面。

## 7. 可选方案

### 方案 A：默认不接 docking

```text
final_enzyme_score = EnzymeCAGE_score
```

适合：

```text
大规模筛选；
快速排序；
结构/pocket/docking 准备不稳定；
老师没有要求机制解释时。
```

优点：

```text
快；
和训练目标一致；
已有 AUC/MRR/Hit@K 验证；
不会引入 docking 准备误差。
```

缺点：

```text
没有显式结合姿势或结合能解释。
```

### 方案 B：docking 作为 post-hoc 注释

```text
先按 EnzymeCAGE_score 排 Top-K；
只对 Top-K 中可准备结构和底物的候选做 docking；
docking_score 作为单独证据列报告；
默认不自动改排名。
```

这是我最推荐的过渡方案。

优点：

```text
不破坏主模型口径；
能给老师/用户提供机制解释；
暂时不需要定硬阈值。
```

缺点：

```text
需要人工解释两个分数。
```

### 方案 C：docking 作为 soft rerank

例如：

```text
final_score = EnzymeCAGE_score × docking_confidence_modifier
```

其中：

```text
1.0  docking 不可用或中性；
0.7  docking 弱/不确定；
0.3  docking 明显不利且 protocol 可靠；
```

优点：

```text
可以降低明显不合理候选。
```

风险：

```text
需要老师批准 docking protocol 和融合规则；
容易因为结构质量、辅因子处理、金属处理不当误伤真阳性。
```

### 方案 D：docking hard filter

```text
docking_score 差于阈值就直接删掉候选
```

当前不推荐。

原因：

```text
docking false negative 很可能存在，尤其是金属酶、辅因子酶、柔性 pocket、需要过渡态姿势的酶促反应。
```

## 8. 如果老师想要证据，建议做最小验证

如果老师希望实验证明 docking 是否值得加，可以设计一个小 benchmark：

1. 选 5–10 个有强证据的反应；
2. 每个反应取：

```text
known positive enzyme；
EnzymeCAGE Top-K 候选；
低分或 matched negative 候选；
```

3. 固定 docking protocol：

```text
结构来源；
active-site box；
底物质子化/互变异构；
金属/辅因子/水处理；
docking score 提取方式；
失败状态 token；
```

4. 看 docking 是否：

```text
能区分 known positive 和 negative；
能提高 EnzymeCAGE Top-K；
是否有大量 false negative；
计算成本是否可接受。
```

如果没有验证，不建议把 docking score 直接硬塞进主分数。

## 9. 给老师可直接发的话

```text
黄老师，我们回源核对了当前 EnzymeCAGE 模型的打分语义。模型最后确实输出 0–1 分数，但这个分数来自 raw logit 的 sigmoid，训练目标是 BCEWithLogitsLoss 下的反应-酶正负配对分类；评估也是按同一反应下候选酶的 pred 降序排序，计算 AUC、Top-K、MRR/Hit 等。因此它应该解释为“反应-酶兼容性/正例可能性/排序分数”，不是 AutoDock 那种显式结合自由能或 docking energy。

模型不是完全忽略结合相关信息：正式配置使用 DRFP、反应中心、底物/分子构象、酶 pocket-node ESM、GVP 结构特征，并有 pocket/substrate 几何注意力，所以它可以间接学习与口袋和底物兼容性有关的统计信号。但它没有显式搜索底物结合姿势，也没有输出 kcal/mol 级 docking 分数，不能直接说它评价了结合难易程度。

我们的建议是：当前 EnzymeCAGE 分数作为主排序分数已经符合模型训练和评估目标；AutoDock-style docking 暂时不要作为默认必须项，也不要替代 EnzymeCAGE 分数。更稳妥的方案是把 docking 放在 Top-K 候选的可选二级证据/软 rerank/解释层：当候选酶结构、活性口袋、辅因子/金属和底物状态都能可靠准备时，再对少量高价值候选做 docking，用于降低或标注明显不合理的候选，而不是一开始对所有候选硬过滤。
```

## 10. 最终建议

当前建议冻结为：

```text
EnzymeCAGE_score = 主排序分数；
AutoDock-style docking = 可选二级证据；
不要把 EnzymeCAGE_score 说成 docking energy；
不要把 docking hard filter 作为默认规则；
如果要融合 docking，需要先做一个小规模验证。
```

这个结论同时符合代码层面的分数语义，也符合 2026-07-03 会议纪要中“AutoDock-style docking 作为辅助 feasibility threshold”的原始定位。
